# OSD 音量条 CPU 排查

日期：2026-10-01。基线：GitHub master `389b7ef`，源码与阶段 21 一致。

用户确认的场景是**连续按键或滚轮调音量时，开启音量条比关闭时 CPU 更高**。

百分比改到左侧，紧随音量图标；静音说明使用右侧剩余空间。复用原 Grid、固定数字列宽及主题画刷。仅修改 [OsdService.cs](E:/kunkun/SonarSwitch/SonicRoute/OsdService.cs:204) 的布局，未实施下方性能方案。

## 主要排查方向

1. **90ms 条动画带来额外绘制。** [ApplyNotice](E:/kunkun/SonarSwitch/SonicRoute/OsdService.cs:167) 每次取当前 ScaleX、StopBar、设置目标，再判断是否创建动画。过渡还要求系统动画开启且渲染 Tier > 0；首次显示、切换目标、Tier 0 或系统关闭动画时直接更新。满足条件时，连续输入使条动画持续活跃，增加动画计算、绘制和对象分配。关闭音量条时没有这一段动画。WPF 的绘制次数、像素量及是否回落到软件渲染都会影响开销；软件渲染使用 CPU。[微软 WPF 渲染说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-taking-advantage-of-hardware)
2. **相同目标也可能重启动画。** 代码比较的是当前动画中间值与本次目标，没有记录上次目标百分比。因此旧动画尚未结束、连续输入得到同一百分比时，仍可能停掉再创建一次 90ms 动画。到达 0%/100% 附近连续操作时尤其值得去重；并非每次相同输入都必然产生新动画，动画已到目标时不会创建。
3. **附加布局与合成成本。** 专用布局有更多控件，数字变化仍涉及文字格式化；开启后默认逻辑高度从 70 增至 82，淡入淡出需要处理更大区域。这个尺寸比例不是 CPU 增幅估计。`AllowsTransparency=true` 也不能单独证明窗口始终使用软件渲染。
4. **没有发现音量条增加常驻采样或空闲刷新循环。** OSD 只有原来的 1100ms 隐藏计时器，没有专用周期刷新或 `CompositionTarget.Rendering` 订阅；动画完成、隐藏、关闭开关及退出都有清时钟逻辑。若问题仅在连续输入时出现，优先排查上述显示路径。

配置加载使用已有内存缓存，未因每次显示额外读配置文件；音量条开关不会改变快速面板电平的 33ms 采样或 2s 会话扫描。

## 建议方案（未实施）

| 优先级 | 方案 | 改善目标 | 代价/边界 |
|---|---|---|---|
| 1 | 记录条的目标与动画活动状态，相同目标不重启动画；无活动时不反复移除时钟 | 减少重复输入、极值附近操作的无效时钟和对象操作 | 目标、模板、隐藏及关闭时需正确失效；不减少正常变化本身的绘制 |
| 2 | 同一帧的多次条更新只使用最新目标，数字保持即时更新 | 减少连续输入导致的动画创建和取消 | 必须保留最后一次音量、目标身份和退出保护；不新增常驻 Timer |
| 3 | 仅将条动画的 DesiredFrameRate 设为 30，保留 90ms 时长 | 减少条过渡所需绘制 | 短动画的帧数会变少，流畅度需实际对照；不改 OSD 淡入淡出或其他窗口动画 |
| 4 | 复用冻结的缓动函数，跳过小于一个物理像素的过渡 | 减少分配和难以察觉的动画 | 是次要成本；像素判断需考虑 DPI 与条宽，数字不能被量化掉 |

`DesiredFrameRate` 是 WPF 的期望调度值，并非对实际帧率的保证；微软将其作为减少部分动画处理资源的方法。[微软 DesiredFrameRate 文档](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.animation.timeline.desiredframerate?view=windowsdesktop-10.0)
