# Windows Link v1

Windows Link is opt-in in Full. The connection and stream code lives in `SonicRoute.AndroidAudio/WindowsLink` so it can reuse the media code that Full already ships. Each peer can send and receive at the same time. The protocol runs over one mutually authenticated TLS TCP connection per peer. The listener defaults to TCP 46916. IPv4 LAN discovery uses UDP 46917 and is a hint only. A manual IP can include a port.

Each peer has a private certificate in user-protected local state. Its ID is the SHA-256 of the leaf DER certificate. The TLS handshake verifies possession. Previously trusted IDs are pinned. New peers exchange randomness with a commitment before revelation, compare the resulting eight-digit code on both computers, and both explicitly confirm. An advertised address cannot establish trust. Pairing attempts and unauthenticated connections have bounded counts and deadlines. If both peers dial at once, the connection initiated by the lower ID wins. An established connection stays in use unless an overlapping dial must be resolved.

Manual reconnect can use the existing IPv4 discovery port to ask a saved peer to dial back when direct TCP attempts fail. The request includes the recipient's certificate ID, the sender's listening TCP port and the issue time, signed by the sender's existing identity. The recipient checks its pin and the signature, rejects stale requests, and rate limits requests for each saved peer. It then dials the LAN source address and requires the same pinned identity over mutual TLS. Older peers ignore this request.

Once authenticated, a frame starts with a one-byte type, a 16-byte stream GUID in .NET byte order, and a four-byte, little-endian payload length. Control and audio have priority between bounded video fragments. Per-peer queues and per-stream receiver buffers are bounded. An open message declares the stream kind, title, and whether the sender allows input. Streams are owned by their creator and close on disconnect or explicit stop by either side. Audio v1 is stereo 48 kHz signed little-endian PCM16. Video defaults to H.264 Annex B. Both ends can negotiate HEVC Annex B using separate encode and decode capabilities, with a little-endian microsecond timestamp and fragment flags. Video options are per stream. The authenticated hello optionally advertises `SupportsNativeVideo`. A native-size pull sets `NativeResolution` and a zero height. Earlier requests with an omitted height keep the 1080p default. A native viewer accepts even frame dimensions up to 8192 pixels per side and 16,777,216 pixels in total. New peers can exchange compressed frames up to 8 MiB, with the original 1 MiB limit for older receivers. If a native HEVC stream changes to a size unsupported by the encoder, bit 3 of the fragment flags marks H.264 data. The viewer resumes decoding at a marked keyframe. Input and volume messages apply only to the matching stream. Input requires permission on the sender. A window stream targets the shared window. A monitor stream maps pointer coordinates to an eligible application on that monitor and keeps keyboard input with the remotely selected control.

`WindowsLinkService` owns start, stop, discovery, trust, connection and stream state. UI code reads peer and stream snapshots and dispatches notifications onto the UI thread. Media adapters receive only selected local process IDs, window handles, PCM or video frames. They have no network protocol or UI dependencies. Media resources exist only while their streams are active. Transport priority, cancellation and limits live in the connection layer.

The audio catalog request uses the sender's cached Windows audio-session enumeration. It skips window discovery and reports whether an app has an audio session independently of whether it is playing. The sender excludes local quick-panel hidden apps from the catalogs. On a session creation or visibility change it sends an empty catalog invalidation to compatible peers. An open quick panel clears its snapshots and reloads only the visible view.

Existing WASAPI process loopback supplies system audio by excluding SonicRoute's process tree and app audio by including the selected process tree. At Windows Link startup, the sender probes the actual process-loopback interface with the PCM capture format and advertises its result in discovery and the authenticated hello. A peer can still receive audio when its own capture interface is unavailable. Receive-side playback reuses the existing PCM ring and WASAPI output. Peers with monitor capture capability (0x2000) also include active monitors in the requested windows catalog. A monitor entry carries its display number, size, primary status and instance identity. The sender verifies that identity when opening the stream. Both windows and monitors use Windows Graphics Capture. The sender and viewer use Media Foundation H.264 or, when a compatible Windows HEVC transform is available, H.265. HEVC offers include the initial dimensions. The viewer selects its transform from the actual offer. Old peers continue to use H.264.

When both peers advertise audio readiness, the receiver replies after the local playback endpoint requests a second render buffer, including when the source app is paused, or reports an initialization failure. The sender publishes the active route after that reply. A destination-only app stream can use an unused secondary render endpoint. The sender saves the app's multimedia and console routes, mutes the spare endpoint if needed, verifies the app moved, and restores the changes it still owns when playback ends. If every active output is already muted by the user, the sender monitors that condition without changing any route or mute setting. When there is no dedicated output, a sender can advertise `CanMuteSourceSpeaker` in an app catalog entry. A destination-only app pull can then explicitly request `AllowSpeakerMute` to temporarily mute the app’s current render endpoint after AudioReady. Other apps using that speaker are silent locally for the duration. Shared playback and requests from older clients retain their existing behavior. Peers with window audio capability (0x4000) can associate an audio pull with a live video stream. A window uses its application's process audio. A monitor uses the sender's system mix. The final viewer releases automatically opened audio, while an explicit audio route remains active.

## File transfers

File offers, acceptance and cancellation use the existing mutually authenticated connection. With the file capability (0x1000), each peer can transfer one file at a time. Multiple selections are sent sequentially. Receivers can accept to their configured folder (initially the Windows Downloads known folder) or choose an explicit destination. An authenticated peer with mutual full trust can deliver directly to the configured folder. A collision in that folder adds a numbered suffix during the final move. A disk read groups up to four 12 KiB wire frames. The writer gives audio and control frames priority between file chunks. The receiver acknowledges each 96 KiB window, writes to a temporary file, and commits without replacing an existing file. The sender reports completion after the receiver acknowledges that commit. Disconnect and cancellation retire the transfer and clean up partial data. Empty files are supported. The limit is 16 GiB per file.

Full trust is negotiated separately from initial pairing. Each PC explicitly generates its own random eight-digit code. It sends a challenge identifier over the existing pinned TLS connection and verifies the code typed on the other PC. Both verifications must succeed in the same exchange. The exchange expires after three minutes, disconnect, cancellation or three incorrect attempts against a code. Both peers save the resulting enrollment identifier and must present matching grants on each new connection. Revoking trust clears the grant and permissions derived from it. Files accepted through full trust are saved to disk. Window input remains scoped to the shared target.

The C# implementation uses a separate logical queue for bulk data. There is one TLS connection per peer and file buffers are allocated on demand. LocalSend documents offering metadata for approval before uploading binary data. KDE Connect schedules file payload jobs independently of its control messages. The Windows process-loopback API captures a selected process tree. Its capture interface is independent of the physical output endpoint. Local monitoring and capture remain separate routing decisions, as in OBS's application capture guidance.
